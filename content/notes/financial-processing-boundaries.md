## 응답 제한 안에서, 내부의 반복 조회를 줄였습니다

2020년 8월부터 2021년 6월까지 다우기술에서 키움저축은행의 혁신금융 신용조회·한도조회·대출 연동 개발에 참여했습니다. 2명이 참여한 프로젝트에서 제 기여도는 40%입니다. 이 글은 그중 반복 단건 조회와 DB 처리 경계를 개선한 경험을 돌아봅니다.

제휴 채널의 한도조회 요청은 은행 내부 처리와 외부 신용기관의 전문 송수신을 거쳐야 했습니다. 외부 채널에는 180초의 응답 제한이 있었습니다. 외부 응답을 기다리는 것만으로 설명을 끝내지 않고, 내부에서 같은 요청을 처리하며 반복하는 경로를 살폈습니다.

180초는 지켜야 할 제약이지 변경 전 평균 응답시간은 아닙니다. 제가 바꾼 내부 처리와 외부기관 대기 시간을 하나의 수치로 섞지 않는 것이 이 경험을 설명하는 출발점입니다.

## 단건 SELECT가 다섯 단계로 반복되는 구조를 바꿨습니다

문제는 단순한 SELECT 한 번보다, 그 SELECT를 건별로 반복하는 구조에 있었습니다. 예를 들어 m명에 대해 각각 n건의 조회를 수행하면 m×n번의 단건 조회가 발생하는 경우가 있었습니다. 이런 처리가 최대 다섯 단계까지 이어져 m×n×o×p×q 형태로 조회가 반복되는 경우도 있었습니다.

이 표현은 당시 반복 조회 구조를 설명하기 위한 예시입니다. 각 문자의 실제 건수나 모든 요청의 SQL 실행 횟수를 뜻하지는 않습니다. 그렇지만 바꿔야 할 대상은 분명했습니다. **반복문 안에서 단건 조회를 계속 실행하는 방식을 그대로 둔 채, 개별 SQL만 보는 것으로는 개선 범위를 충분히 설명할 수 없었습니다.**

저는 쿼리 조합과 튜닝, 처리 구조 개선을 통해 불필요한 건별 조회를 줄였습니다. 설명의 단위도 ‘SQL 하나를 얼마나 빠르게 실행했는가’뿐 아니라 ‘한 업무를 끝내기 위해 DB에 얼마나 반복 접근하는가’로 넓어졌습니다.

| 변경 전 | 변경 방향 |
|---|---|
| 대상마다 단건 SELECT를 반복 | 쿼리 조합으로 불필요한 건별 조회 축소 |
| 최대 다섯 단계로 이어지는 반복 조회 | 조회를 호출하는 처리 구조 개선 |
| 반복되는 경로 안의 SQL | 쿼리 튜닝과 구조 개선을 함께 적용 |

이 글에서는 개별 SQL의 세부 설계보다 쿼리 조합과 호출 구조를 함께 개선한 접근에 집중합니다. m×n 형태의 조회를 모두 한 번으로 바꿨거나, 전체 알고리즘의 시간복잡도를 특정 차수로 낮췄다는 의미는 아닙니다.

## 오토커밋으로 흩어진 처리를 업무 단위 트랜잭션으로 묶었습니다

반복 조회를 줄이는 것과 별개로, 조회·저장 업무의 처리 경계도 정리했습니다. 기존에는 업무 단위의 명시적인 트랜잭션 경계 없이 DB 처리가 흩어져 있었고, 저장은 오토커밋 방식으로 이루어지고 있었습니다.

여기서 ‘트랜잭션이 없었다’는 말은 DB에 트랜잭션 자체가 존재하지 않았다는 뜻이 아닙니다. **여러 조회·저장으로 이루어진 업무를 하나의 성공·실패 단위로 다루는 커밋·롤백 범위를 명시적으로 적용하지 않았던 상태**를 말합니다.

저는 흩어진 조회·저장을 업무 단위의 하나의 트랜잭션으로 묶고, 해당 단위의 커밋과 롤백 범위를 적용했습니다. 이는 호출 횟수 개선과 다른 축의 변경이었습니다. 앞선 개선이 불필요한 DB 접근을 줄이는 작업이었다면, 이 변경은 묶은 업무가 어디까지 함께 완료되거나 취소되어야 하는지를 정해 안정성을 확보하는 작업이었습니다.

두 변경을 모두 ‘DB 최적화’라고만 적으면 차이가 사라집니다. **조회 경로는 효율을 위해 정리했고, 커밋·롤백 경계는 업무 단위의 안정성을 위해 정리했습니다.**

트랜잭션 적용 API, 격리 수준, 전파 속성, 외부 전문 송수신의 위치는 이 글의 설명 범위에 포함하지 않습니다. 이 경험을 외부기관 처리까지 같은 트랜잭션으로 묶었다거나 분산 원자성을 보장했다는 설명으로 확대하지 않습니다. 장애가 몇 건 줄었는지나 어떤 실패 테스트를 통과했는지도 별도 근거 없이 추가하지 않습니다.

## 개선 수치는 각각의 범위 안에서 읽습니다

기존 조회 로직 대비 약 95% 개선을 이루었고, 10초 이내 수준의 처리와 일 2만여 건의 연동 처리를 경험했습니다. 다만 이 수치들은 각각의 범위에서 해석해야 하며, 하나의 동일 조건 전후 실험 결과로 제시하지 않습니다.

| 지표·조건 | 설명 범위 |
|---|---|
| 180초 응답 제한 | 외부 채널의 제약. 변경 전 평균 응답시간이 아님 |
| 기존 조회 로직 대비 약 95% 개선 | 해당 조회 로직의 개선. 전체 서비스 응답시간으로 확대하지 않음 |
| 10초 이내 수준 · 일 2만여 건 | 처리 수준과 일 처리량. 동일 부하 전후 실험이나 TPS를 뜻하지 않음 |

따라서 ‘180초 걸리던 서비스를 10초로 줄였다’라고 쓰지 않습니다. 조회 조합, 개별 SQL 튜닝, 호출 구조 개선의 효과를 각각 수치로 분리하거나 트랜잭션 변경에 성능 향상을 직접 귀속하지도 않습니다.

프로젝트의 전체 맥락과 담당 범위는 [연결된 프로젝트 사례](../../cases/financial-integration/)에도 정리해 두었습니다. 이 글에서는 반복 조회 구조 개선과 업무 단위 커밋·롤백 적용을 중심으로 설명했습니다.

## 다시 남긴다면, 조회 경로와 실패 결과를 증거로 연결하겠습니다

지금 이 경험을 다시 정리하면서 더 남기고 싶은 것은 두 종류의 증거입니다. 아래는 당시 모두 수행했다는 검증 목록이 아니라, 현재 관점에서 보강하려는 기준입니다.

첫째는 **같은 입력에서 변경 전후의 조회 경로와 비용**입니다. 한 요청에서 반복되는 SQL 실행 횟수, 결과 건수와 처리시간을 함께 남기면 쿼리 튜닝과 호출 구조 개선의 효과를 더 분명하게 설명할 수 있습니다. 측정에는 요청 종류·입력 규모·부하 조건과 내부 처리/외부 대기의 구분도 필요합니다.

둘째는 **업무 단위 트랜잭션의 성공·실패 결과**입니다. 정상 처리에서는 필요한 저장이 함께 완료되는지, 중간 오류에서는 정한 범위가 롤백되는지 확인한 기록이 있으면 설계한 경계와 실제 동작을 연결할 수 있습니다. 외부기관 타임아웃이나 재요청은 같은 DB 트랜잭션 설명만으로 해결됐다고 보지 않고 별도로 확인할 항목입니다.

이 경험에서 가져온 기준은 단순히 ‘쿼리를 빠르게 만들자’가 아닙니다. **한 업무를 끝내는 데 불필요한 조회를 얼마나 반복하는지, 그 업무가 실패하면 어디까지 함께 취소되어야 하는지를 나눠 보는 것**입니다. 실행 경로의 효율과 업무 단위의 안정성을 함께 다루되, 각각을 뒷받침하는 근거도 구분해 남기려 합니다.
