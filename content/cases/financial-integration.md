## 빠른 응답은 외부기관만의 문제가 아니었습니다

제휴 채널의 한도조회 요청은 은행 내부 처리와 외부 신용기관 전문 송수신을 거쳐야 했습니다. 외부 채널에는 180초의 응답 제한이 있었고, 내부 처리의 반복까지 겹치면 이 제한을 넘을 수 있었습니다.

다우기술에서 키움저축은행의 신용조회·한도조회 연동 개발을 맡았습니다. 2명이 참여한 프로젝트에서 제 기여도는 40%입니다. 제 담당 범위는 은행 내부의 전문·조회 연동 개발이었습니다.

## 통신 경계 안쪽에서 줄일 수 있는 비용을 찾았습니다

전문 조립과 분해, 반복 가공, 건별 SELECT와 DML이 누적되는 내부 경로를 분석했습니다. 단순히 외부 응답을 기다리는 시간이 아니라, 같은 업무를 위해 여러 번 지나가는 처리 단계를 줄이는 데 집중했습니다.

| 이전의 처리 비용 | 변경한 방향 |
|---|---|
| 중복된 가공과 여러 단계의 Loop | 중복 단계 제거와 처리 흐름 단순화 |
| 매 건별 SELECT와 불필요한 DML | 조회 통합과 중복 DB 접근 제거 |
| DML별 분산된 DB 처리 | 업무 흐름 단위로 DB 처리 경계 조정 |

## 업무의 경계를 정리하는 일이 채널 확장의 기반이 됐습니다

카카오페이 연동에서 출발한 흐름은 핀다·핀크·웰컴 등 제휴 채널로 확장됐습니다. 채널을 늘릴 때마다 같은 전문 처리와 저장 책임을 복제하지 않도록, 반복되는 내부 로직을 정리한 경험입니다.

## 결과를 읽는 범위

**기존 조회 로직 대비 약 95% 개선**을 이루었고, 10초 이내 수준의 처리와 일 2만여 건의 연동 처리를 경험했습니다. 이를 전체 서비스의 종단 응답시간이나 TPS로 확대하지 않습니다. 180초는 채널의 응답 제한이며, 동일 조건으로 실측한 변경 전 평균값이라는 뜻이 아닙니다.

업무 단위 DB 처리 통합 역시 외부기관과 은행 DB를 묶은 분산 원자성을 보장한다는 의미는 아닙니다. 정확한 커밋 횟수·격리 수준·락 감소량은 확인할 수 없어 제시하지 않습니다.

이 경험은 병목을 설명할 때 외부 의존성의 탓으로 멈추지 않고, **내가 바꿀 수 있는 실행 경로와 책임의 경계**를 먼저 찾는 기준이 됐습니다.
