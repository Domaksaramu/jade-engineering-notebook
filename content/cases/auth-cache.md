## 서버가 멈췄을 때, 먼저 본 것은 증설 가능성이 아니었습니다

차세대 소비자금융 시스템 오픈 후 CPU 사용량이 급증하고 예기치 않게 서버가 중단됐습니다. 이 문제에서 중요한 것은 느린 API 한 개가 아니라, 인증을 거치는 금융 업무 전체의 안정성이었습니다.

저는 장애 원인 분석과 캐시 삭제 로직 개선을 단독으로 담당했습니다. Java 8, Spring Boot 2.3, Spring Security 환경에서 요청 처리와 JVM 지표를 함께 살폈습니다.

## 증상에서 객체가 남는 경로로

CPU 상승만으로 원인을 단정하지 않았습니다. Heap 누적과 GC 증가를 함께 확인하고, Heap Dump에서 인증 사용자 정보를 담는 LRUCache의 과도한 누적을 찾았습니다. 그다음에는 캐시가 왜 만들어지는지보다 **언제 없어져야 하는데 남아 있는지**를 추적했습니다.

| 관찰 | 확인한 변경 대상 |
|---|---|
| 인증 사용자 정보가 캐시에 과도하게 누적 | 오래된 항목을 제거하는 정책 |
| 일회성 조회가 끝나도 인증 정보가 잔존 | 요청 처리 후 명시적 정리 경로 |
| Heap·GC·CPU 지표가 함께 악화 | 수정 후 자원 지표 재확인 |

## 요청 종료 정리와 캐시 퇴거 정책을 나눠 고쳤습니다

일회성 조회 API의 인증 캐시 정리 경로를 보완했습니다. 별도로 오래된 항목을 제거하는 LRU 삭제 로직을 수정했습니다. 특정 요청이 끝났을 때의 정리와 캐시 전체의 크기 제어는 서로 다른 책임이기 때문입니다.

아래 흐름은 보관 경력 기록을 바탕으로 재구성한 개념도입니다. 실제 장애 당시 코드나 전체 예외 처리를 재현한 것은 아닙니다.

```text
인증 정보 생성 → 요청 처리 → 정상 반환 뒤 정리
                     ↓
             캐시의 오래된 항목 제거 정책 점검
                     ↓
               캐시 · Heap · GC 재확인
```

## 달라진 것과, 아직 단정할 수 없는 것

기록된 Heap 사용량은 10GB에서 3.5GB로 줄었습니다. LRU Cache 크기는 약 90% 감소한 것으로 정리돼 있습니다. 이 경험에서 얻은 핵심은 큰 숫자보다, **CPU라는 증상을 객체 수명과 삭제 정책이라는 변경 지점으로 연결한 과정**입니다.

> Heap 수치의 평균/피크, 동일 부하 여부는 보관 기록만으로 확인되지 않습니다. GC 200건→80건은 관측 시간이 없어 초당 GC 횟수나 처리량으로 환산하지 않습니다.

현재 재검토한다면 예외 종료에서도 정리가 실행되는지, 공유 캐시 접근과 퇴거가 동시성 조건에서 안전한지를 별도 테스트로 확인하겠습니다. 이는 당시 검증 완료 주장과 구분한 후속 점검 관점입니다.
