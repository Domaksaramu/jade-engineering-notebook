# 콘텐츠 후속 계획

2026-11-06. 기존 문서에 확정돼 있던 후속 범위와 이번에 제안하는 글 후보를 구분한다. 아래 후보는 작성·발행 완료나 확정 일정이 아니다.

## 이미 남겨둔 후속 범위
- 기존 블로그 글의 목록·원본·URL을 확인한 뒤 필요한 글을 초안으로 이관.
- 업무 메모 → 초안 → 사실/기밀 검토 → 검증 → 발행 흐름.
- V1의 디자인과 메인 요약은 유지. 현재 경력 사례 3개와 경험 노트 2개의 공개 문안을 임의로 늘리지 않음.

기존 문서에는 추가 기술 글의 확정 목차·발행 일정까지 정해져 있지 않았다.

## 제안 1 — 기존 사례는 근거가 있을 때만 깊게
| 사례 | 보강할 질문 | 필요한 자료 / 주장 제한 |
|---|---|---|
| 인증 캐시 | CPU 증상에서 캐시 수명 문제를 어떻게 좁혔나? 요청 종료 정리와 LRU 퇴거를 왜 분리했나? | 당시 관찰 순서·변경 범위·검증 기록. 예외/동시성은 과거 완료와 현재 재검토를 분리. GC rate나 동일 부하 성능은 추정하지 않음 |
| 금융 연동 | 반복 가공·DB 접근 중 어떤 경로를 왜 줄였나? 저장 경계를 선택할 때 대안은 무엇이었나? | 공개 가능한 전후 처리 단계·본인 책임·측정 범위. 실제 커밋 횟수/격리 수준/분산 원자성을 만들어 쓰지 않음 |
| ML 운영 | 배포 완료와 실제 정상 응답을 어떤 기준으로 나눴나? 검증·관측을 어디까지 연결했나? | 환경별 CI/CD·E2E·리포트 근거. 개발계 9개와 운영계 검증 범위를 섞지 않음 |

자료가 없으면 수치를 늘리지 않는다. 본문이 길어지면 별도 경험 노트로 분리하고 사례에는 판단의 핵심만 남긴다.

## 제안 2 — 별도 글 후보
1. **공통파트 PL로서, 다른 개발자가 사용할 기준을 만드는 일**: 본인이 정한 공통 기준·적용 방식·협업 범위를 원천 자료에서 확인 후 구성.
2. **이기종 DB 대응에서 바뀌지 않아야 할 동작을 정하는 법**: 실제 지원 DB·호환 이슈·테스트 기록 확인이 선행. 존재하지 않는 SQL/실패 사례를 만들지 않음.
3. **배포 자동화 다음에 남는 반복 확인을 줄이는 일**: 현재 ML 사례와 중복되지 않게 E2E 확인·운영 리포트의 특정 판단 하나에 집중.
4. **기존 블로그의 선별 이관**: 전체 복제보다 현재 경력 스토리에 연결되는 글부터. 기존 URL과 발행일의 의미를 보존.

## 우선순위 제안
배포·발행 흐름 검증 → 기존 글 목록 조사 → 근거가 가장 충분한 글 1건을 초안으로 작성 → 사용자 내용 검토 → 공개. 한 번에 많은 글을 늘리지 않는다.

## 모든 글의 공통 구조
맥락/본인 역할 → 관찰 → 검토한 대안과 선택 → 변경 → 검증/한계 → 다음 판단의 기준. 수치보다 판단의 근거를 우선한다.
